## Этап 3. Сбои и восстановление

Реализован сценарий восстановления заказа, при котором оплата уже прошла, но на момент выдачи товара закончился доступный ключ.

### Что реализовано

* Если оплата прошла успешно, но ключ отсутствует в inventory, заказ не теряется и не переходит в необрабатываемую ошибку.
* Заказ переводится в состояние `out_of_stock`.
* Неуспешная попытка выдачи сохраняется в `delivery_attempts` с причиной ошибки.
* Оплаченные заказы, которые не были выданы, доступны через административный API.
* После пополнения inventory заказ можно безопасно повторно выдать вручную.
* Повторная выдача идемпотентна: один заказ не получает второй ключ.
* Уже выданные и неоплаченные заказы отсутствуют в списке на восстановление.

### Сценарий воспроизведения

#### 1. Создать оплаченный заказ

Создать заказ через API:

```bash
curl -X POST http://localhost:8000/api/orders \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d "{\"sku\":\"KEY-CS2-PRIME\"}"
```

Из ответа взять `data.id`.

Затем выполнить симулированную оплату:

```bash
curl -X POST http://localhost:8000/api/orders/{ORDER_ID}/pay \
  -H "Accept: application/json"
```

Оплата обрабатывается через тот же webhook-механизм, который используется в основном purchase flow.

#### 2. Воспроизвести отсутствие товара

Если для товара нет доступных inventory items, попытка выдачи завершится состоянием:

```text
order.status = out_of_stock
```

При этом оплата заказа сохраняется, а информация о неудачной попытке выдачи записывается в `delivery_attempts`.

Это recoverable-состояние: заказ можно обработать после пополнения inventory.

#### 3. Получить список заказов, ожидающих восстановления

Административный endpoint:

```http
GET /api/admin/orders/paid-not-delivered
```

Пример:

```bash
curl http://localhost:8000/api/admin/orders/paid-not-delivered \
  -H "Accept: application/json"
```

Endpoint возвращает заказы, которые были оплачены, но не завершили выдачу.

В текущей реализации в список попадают состояния:

* `out_of_stock`
* `delivery_failed`

Уже выданные (`delivered`) и неоплаченные (`created`, `payment_failed`) заказы в этот список не попадают.

Пример ответа:

```json
{
  "data": [
    {
      "id": "9bbc1a07-f8e7-4536-81f3-b73abdaa41aa",
      "sku": "KEY-CS2-PRIME",
      "amount": 1290,
      "currency": "RUB",
      "status": "out_of_stock",
      "created_at": "2026-09-17T..."
    }
  ]
}
```

#### 4. Пополнить inventory

После добавления нового ключа в inventory заказ снова можно обработать.

В production-сценарии этот шаг выполняется административным инструментом/операцией пополнения склада. В тестах наличие нового ключа эмулируется созданием `InventoryItem` со статусом `available`.

#### 5. Выполнить ручной retry

Для восстановления заказа используется:

```http
POST /api/orders/{ORDER_ID}/retry-delivery
```

Необходимо передать новый `Idempotency-Key`:

```bash
curl -X POST http://localhost:8000/api/orders/{ORDER_ID}/retry-delivery \
  -H "Accept: application/json" \
  -H "Idempotency-Key: manual-retry-{UNIQUE_ID}"
```

При наличии ключа в inventory заказ переходит:

```text
out_of_stock
    ↓
paid
    ↓
delivering
    ↓
delivered
```

В ответе возвращается выданный ключ:

```json
{
  "status": "delivered",
  "code": "XXXX-XXXX-XXXX"
}
```

### Идемпотентность повторной выдачи

Каждая операция выдачи использует `Idempotency-Key`.

Повторный запрос с тем же ключом:

```bash
curl -X POST http://localhost:8000/api/orders/{ORDER_ID}/retry-delivery \
  -H "Accept: application/json" \
  -H "Idempotency-Key: manual-retry-123"
```

не создаёт новую выдачу и возвращает тот же результат.

Также защищён сценарий, когда после успешной выдачи используется уже новый `Idempotency-Key`: существующий выданный inventory item возвращается повторно, а второй ключ заказу не назначается.

### Тестовое покрытие

Сценарий восстановления проверяется feature-тестами:

* отсутствие inventory переводит оплаченный заказ в `out_of_stock`;
* неуспешная выдача сохраняется как `delivery_attempt`;
* заказ нельзя повторно выдать напрямую из `out_of_stock`;
* восстановление выполняется через специальный `retry-delivery`;
* после пополнения inventory retry выдаёт ключ;
* `delivery_failed` также является восстанавливаемым состоянием;
* retry идемпотентен;
* повторный retry после успешной выдачи не создаёт новую попытку и не выдаёт второй ключ;
* административный список содержит только оплаченные заказы без успешной выдачи;
* `delivered` и неоплаченные заказы в административный список не попадают.
